<SplitSection
    label="A New Source of Truth"
    title={["You engineer the shape while the agent builds the software."]}
    cta={{ href: "/language/", text: "Learn the Language" }}
>
    Humans are good at engineering software, and we have decades of collective
    experience and intuition accumulated around exactly that.

    And this is *exactly* what Piton lets you focus on.  The human describes
    the intent, the behaviour, the shape, the structure, and above all, infuses
    it with their **judgement and sense of taste.**

    A `.pi` file is the structure a machine can follow, and the engineer
    can compose.  It, not the implementing code, is the referenceable and
    **repeatable** source of truth for the engineer's intent.

    What you maintain is the specification. Everything downstream is a
    disposable build artifact, including the Agent-generated code.

    <Fragment slot="example">
        ```piton
        abstract anchor Component as component:
            description:: string
            accessibility:: string

        component Button:
            description:
                A single action, labelled with a verb.
                Triggers an action when clicked.

            accessibility:
                Reachable by keyboard. The label is
                the accessible name; never let an
                icon alone carry it.

        anchor IconButton extends Button:
            description:
                + {super.description}
                The label moves to a tooltip;
                the icon is decorative.
        ```
    </Fragment>
</SplitSection>

<SplitSection
    label="The Method is the Output"
    title="Architect the guidance instead of just writing prompts."
    cta={{ href: "/belay/", text: "The Belay Framework" }}
    reverse
>
    It's one thing to build a small tool with a few prompts, but once a project
    or team starts to scale, agentic structure becomes a necessity. That's
    exactly why `AGENTS.md` files exist.

    But that Markdown file quickly becomes a body of unstructured prose written
    by different people, each with a different voice and different assumptions,
    maintained separately from the specification it intends to support.

    The Belay Framework is built on Piton to **unify** the what *and* the how;
    the specification and the guidance are the complete, versionable, shareable,
    and buildable definition of an agentic workflow.

    <Fragment slot="example">
        ```piton
        use @piton/belay

        from /shape/components/Button import Button
        from /context import TechStack, CodingGuidelines


        skill BuildButtonComponent:
            description:
                Implement the ${Button} component to
                according to the spec

            useWhen:
                You need to implement or make changes to
                the ${Button} component or any of its
                descendants

            prompt:
                ${self.description} adhering to the
                @{TechStack}. If the component is already
                implemented, check the implementation
                against differences in the spec and
                refactor accordingly.

                Follow all @{CodingGuidelines}
        ```
    </Fragment>
</SplitSection>

    Piton treats the [agent as the compiler](./thesis/agent-as-compiler). Our
    goal as engineers is now to constrain the probability of output to the
    bounds of **repeatable correctness**.

    While the agent builds, the team continues to refine the constraints and
    workflows, driving intent and result towards convergence.
</RaisedCardSection>

        ### CLI
        Compile, check, format, inspech reach, and build individual files or entire

        Real-time diagnostics, validation, navigation, and editor-aware language
