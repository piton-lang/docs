<p class="pi-split__label">The compile step</p>

<h2 class="pi-split__title">You write the shape.<br />The agent builds the software.</h2>

<p class="pi-split__body">A Piton source is one document: the structure a machine can check, and the
prose only a person can write, in the same file. Belay compiles it into the
agentic Markdown your tools already read — skills, commands, instructions and
agents.</p>

<p class="pi-split__body">What you maintain is the specification. Everything downstream of it is build
output, and build output cannot drift from the thing that generated it.</p>

<a class="pi-split__cta" href="/belay/">The Belay framework</a>

</div>
<div class="pi-split__example">

```piton
use @piton/belay

skill ReviewDiff:
    description: Reviews a change for correctness and reuse.
    useWhen: the user asks for a review of the current diff

    prompt:
        Read the diff, not the whole tree. Report a finding only when
        you can name the input that breaks it, and say plainly what
        the failure looks like.

    checks:
        - correctness
        - reuse
        - efficiency
```

<p class="pi-split__label">The language</p>

<h2 class="pi-split__title">The prose inherits too.</h2>

<p class="pi-split__body">An anchor is the one user-defined type: a named declaration that takes part in
inheritance, typing, exports and composition. A type constraint holds a
paragraph to the same contract it holds a number to, and a child extends a
sentence the way it extends any other property.</p>

<p class="pi-split__body">So the paragraph you wrote once has a single home. Everything that needs it
refers to it, and there is no second copy left to fall out of date.</p>

<a class="pi-split__cta" href="/language/">The language reference</a>

</div>
<div class="pi-split__example">

```piton
abstract anchor Component as component:
    description:: string
    accessibility:: string

component Button:
    description: A single action, labelled with a verb.

    accessibility:
        Reachable by keyboard. The label is the accessible
        name; never let an icon alone carry it.

anchor IconButton extends Button:
    description:
        + {super.description}
        The label moves to a tooltip; the icon is decorative.
```

</div>

<p class="pi-cycle__label">The lifecycle</p>

<h2 class="pi-cycle__title">The specification is the source. Everything else is output.</h2>

<p class="pi-cycle__lede">Piton treats the agent as the compiler. What you keep is a document a machine
can check and a person can read; what the agent produces is a build. The
distinction matters because only one of the two is worth arguing about in
review.</p>

<ol class="pi-cycle__steps">
<li class="pi-cycle__step">
<p class="pi-cycle__step-name">Specification</p>
<p class="pi-cycle__step-body">Structure and prose in one document. Anchors, inheritance and type constraints
hold the parts a compiler can verify against the parts only a person can write.</p>
</li>
<li class="pi-cycle__step">
<p class="pi-cycle__step-name">Compilation</p>
<p class="pi-cycle__step-body">Belay lowers the spec into agentic Markdown. The agent reads that and does the
work — it is the compiler, and the specification is its input.</p>
</li>
<li class="pi-cycle__step">
<p class="pi-cycle__step-name">Software</p>
<p class="pi-cycle__step-body">The application, its configuration, its documentation. Build artefacts:
regenerate them and nothing of record has been lost.</p>
</li>
<li class="pi-cycle__step">
<p class="pi-cycle__step-name">The team</p>
<p class="pi-cycle__step-body">Read it, disagree with it, decide against it. The spec is the one artefact
small enough to hold in your head and exact enough to be wrong.</p>
</li>
</ol>

<p class="pi-cycle__return">A change starts at the specification, never in what it produced — which is what
makes this a lifecycle and not a hand-off.</p>

<p class="pi-versus__label">The usual way</p>

<h2 class="pi-versus__title">The prompt is thrown away. The code is the record.</h2>

<p class="pi-versus__body">You describe what you want, an agent writes it, and what survives is the
output. The reasoning that produced it — the constraints, the options rejected,
the sentence explaining why — lived in a conversation, and the conversation is
gone.</p>

<p class="pi-versus__body">So the code becomes the specification by default. It is the only artefact left
that describes the system, and it describes it in the most verbose and least
stable form available.</p>

<p class="pi-versus__note">On a team</p>

<ul class="pi-versus__list">
<li>Intent is recoverable only by reading the implementation.</li>
<li>Review argues about output, because output is all there is to argue about.</li>
<li>Two people asking for the same thing get two different systems.</li>
<li>Growth means more code to hold in your head, and no summary of it that is guaranteed to still be true.</li>
</ul>

</div>

<div class="pi-versus__side pi-versus__side--after">

<p class="pi-versus__label">The Piton way</p>

<h2 class="pi-versus__title">The spec is the record. The code is output.</h2>

<p class="pi-versus__body">The specification is what you write, review and keep. It carries the structure a
compiler can check and the prose explaining the parts it cannot, in one
document, under the version control you already use.</p>

<p class="pi-versus__body">What the agent builds is a build. When it is wrong you do not patch it — you
correct the spec and compile again, which is the reflex you already have about
every other compiler's output.</p>

<p class="pi-versus__note">On a team</p>

<ul class="pi-versus__list">
<li>Intent is written down, in the artefact everyone already reviews.</li>
<li>Review argues about the specification, which is short enough to read in full.</li>
<li>Two people extend the same anchors instead of re-deriving them.</li>
<li>Growth means more spec, and spec composes — inheritance, imports and type constraints hold it together.</li>
</ul>
