<SplitSection
    label="A New Source of Truth"
    title={["You engineer the shape while the agent builds the software."]}
    cta={{ href: "/language/", text: "Learn the Language" }}
>
    Humans are good at engineering software, and we have decades of collective
    experience and intuition accumulated around exactly that.

    And this is *exactly* what Piton lets you focus on.  The human describes
    the intent, the behaviour, the shape, the structure, and above all, infuses
    it with their **judgement and sense of taste.**

    A `.pi` file is the structure a machine can follow, and the engineer
    can compose.  It, not the implementing code, is the referenceable and
    **repeatable** source of truth for the engineer's intent.

    What you maintain is the specification. Everything downstream is a
    disposable build artifact, including the Agent-generated code.

    <Fragment slot="example">
        ```piton
        abstract anchor Component as component:
            description:: string
            accessibility:: string

        component Button:
            description:
                A single action, labelled with a verb.
                Triggers an action when clicked.

            accessibility:
                Reachable by keyboard. The label is
                the accessible name; never let an
                icon alone carry it.

        anchor IconButton extends Button:
            description:
                + {super.description}
                The label moves to a tooltip;
                the icon is decorative.
        ```
    </Fragment>
</SplitSection>

<SplitSection
    label="The language"
    title="The prose inherits too."
    cta={{ href: "/language/", text: "The language reference" }}
    reverse
>

    An anchor is the one user-defined type: a named declaration that takes part in
    inheritance, typing, exports and composition. A type constraint holds a
    paragraph to the same contract it holds a number to, and a child extends a
    sentence the way it extends any other property.

    So the paragraph you wrote once has a single home. Everything that needs it
    refers to it, and there is no second copy left to fall out of date.

    <Fragment slot="example">
        ```piton
        use @piton/belay

        skill ReviewDiff:
            description: Reviews a change for correctness and reuse.
            useWhen: the user asks for a review of the current diff

            prompt:
                Read the diff, not the whole tree. Report a finding only when
                you can name the input that breaks it, and say plainly what
                the failure looks like.

            checks:
                - correctness
                - reuse
                - efficiency
        ```
    </Fragment>
</SplitSection>

    can check and a person can read; what the agent produces is a build. The
    distinction matters because only one of the two is worth arguing about in
    review.

<TwoColumnSection>

<SectionColumn
    label="The usual way"
    title="The prompt is thrown away. The code is the record."
    recessed
>

You describe what you want, an agent writes it, and what survives is the
output. The reasoning that produced it — the constraints, the options rejected,
the sentence explaining why — lived in a conversation, and the conversation is
gone.

So the code becomes the specification by default. It is the only artefact left
that describes the system, and it describes it in the most verbose and least
stable form available.

<ColumnNote slot="note" label="On a team">

- Intent is recoverable only by reading the implementation.
- Review argues about output, because output is all there is to argue about.
- Two people asking for the same thing get two different systems.
- Growth means more code to hold in your head, and no summary of it that is guaranteed to still be true.

</ColumnNote>

</SectionColumn>

<SectionColumn
    label="The Piton way"
    title="The spec is the record. The code is output."
>

The specification is what you write, review and keep. It carries the structure a
compiler can check and the prose explaining the parts it cannot, in one
document, under the version control you already use.

What the agent builds is a build. When it is wrong you do not patch it — you
correct the spec and compile again, which is the reflex you already have about
every other compiler's output.

<ColumnNote slot="note" label="On a team">

- Intent is written down, in the artefact everyone already reviews.
- Review argues about the specification, which is short enough to read in full.
- Two people extend the same anchors instead of re-deriving them.
- Growth means more spec, and spec composes — inheritance, imports and type constraints hold it together.

</ColumnNote>

</SectionColumn>

</TwoColumnSection>
